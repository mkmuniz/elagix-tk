    feat(agent): allow read-only commands while a console prompt is pending
    
    Found via a UX walkthrough of the persona-selection prompt: any `/` command
    typed while PendingConsolePrompt was active auto-resolved the prompt with
    "none" and discarded it -- including a harmless "just checking" command
    like `/extension list` (to see what's already installed before answering
    the menu). The operator loses their pending choice just for looking.
    
    is_read_only_while_prompt_pending() whitelists the specific (command,
    subcommand) forms confirmed genuinely read-only against
    command_catalog.rs's own descriptions: /help, /logs, /connect, bare
    /model, bare /backend, /update (bare or "status"), "/task list"/"/task
    inspect", "/schedule list", "/credential list", "/extension list",
    "/proposal list"/"/proposal show". Every other form of those same commands
    (install, revoke, cancel, approve, use, apply, ...) still falls through to
    the existing auto-resolve-with-none behavior, since those DO mutate state
    or could themselves want a second pending prompt (only one slot exists).
    
    Implementation: the guard on the pending-prompt match arm in main.rs's
    REPL loop now excludes read-only lines, so they never reach
    pending_console_prompt.take() -- they fall through to the normal
    `/`-dispatch arm below unchanged, and the prompt is untouched, still
    answerable on the operator's next line.
    
    2 new tests (accepts every whitelisted form, rejects every mutating one +
    non-command chat). Full suite (474 unit + ~100 integration) green, clippy
    clean on both feature sets.

    feat(agent): /committee -- 2-stage Cabinet composition (M4)
    
    Backlog: "Bastion -- hedge fund pack (comite de personas investidoras)" (B2).
    M4 slice -- the "Estagio 2" dissent gate the original design called for,
    on top of M3's simpler "just reuse /cabinet" pass.
    
    New src/agent/committee.rs, wired as a new /committee <pergunta> console
    command (same trusted-host tier as /extension):
    
    1. Stage 1 -- convenes the 4 signal personas (fundamentalist, contrarian,
       macro, growth) for exactly 1 round (no reply round -- they must not see
       each other yet). Parses each turn's {signal, confidence, reasoning}
       JSON (tolerates markdown-fenced JSON, same approach as the router's own
       parser, since no shared utility for that exists in bastion-core).
    2. Disagreement gate -- if the parsed signals don't all agree, convenes a
       SECOND, narrower Cabinet with only the personas that produced a signal,
       for a real multi-round debate, then synthesizes a verdict from it. If
       they already agree, skips straight to stage 3 with stage 1's signals.
    3. Stage 3 -- Risk Manager, single-persona dispatch (not Cabinet, no
       debate).
    4. Stage 4 -- Portfolio Manager, same single-dispatch shape, folding in
       the Risk Manager's output. Final decision printed to the console.
    
    This is the first place in bastion-agent that calls bastion-core's Cabinet
    primitives (build_table, orchestrator::deliberate, synth::synthesize)
    directly, composing them twice in one turn -- confirmed via research
    before writing this that no precedent for that composition existed
    anywhere in the codebase (the only production path today is the automatic
    one inside PersonaResponder::respond). Every RouterDecision built here is
    hand-constructed, tagged ConveneReason::ManualOverride.
    
    Egress gating: orchestrator::deliberate and runner::run's Single path both
    call check_egress internally already. The one gate this module adds
    itself is the same one PersonaResponder::respond adds before calling
    synth::synthesize (which does not gate internally) -- see the stage-2
    synthesis call site.
    
    Validated: builds and passes the full existing test suite/clippy against
    the real (now-pushed) bastion-core rev. Smoke-tested against a real LLM
    (Gemini) -- confirmed the error path handles a real provider failure
    (daily free-tier quota exhausted) cleanly, without panicking. Full
    successful end-to-end run (all 4 stages completing) still pending --
    blocked on the quota resetting, not on the code.
